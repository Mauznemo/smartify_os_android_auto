The Android Auto extension for SmartifyOS, built on the `android_auto` plugin (https://github.com/Mauznemo/FlutterAndroidAuto, usually checked out at `../../FlutterAndroidAuto`).

It follows SmartifyOS's own conventions (its `CLAUDE.md`) and the extension convention in its `EXTENSIONS.md`. Most importantly: only `package:smartify_os_core/<library>.dart`, never `src/`; `smartify_os_core` is a lower bound only in `pubspec.yaml`, and packages core also uses are `any`; and no `riverpod_generator`, so the providers are written out by hand. Working on it on its own needs a `pubspec_overrides.yaml`, see `README.md`. Anything the car needs installed on Linux (a package, a program run through `SmartifyOsShell`, a udev rule) is listed under `smartify_os` in `pubspec.yaml`, which the CLI installs from; when the plugin's own Linux requirements change, change that list too.

Things about the plugin that are easy to break and do not show until a phone is involved:

- **The controller is made once, at boot, with wireless in its transports, and never disposed.** Making it is what publishes the Android Auto service on Bluetooth, and a phone only reads that while pairing, so doing it lazily (when the window opens) means phones paired before the first start never offer wireless. The driver's "without a cable" switch only decides whether a session offers Wi-Fi, never whether the service is published.
- **`start()` offers Wi-Fi on its own** because the transports include it, unless it is given `transports: {usb}`. When a phone is on Bluetooth, the network is made and `setWirelessConfig` called *before* `start()`, so the start offers the right one.
- **The plugin's "connected" is not a picture.** It is reported once the phone agrees to project, up to twenty seconds (over Wi-Fi) before the first frame. What the driver sees follows `controller.hasVideo` instead, which changes on the controller's notifications, not on an event: the service listens to the controller for it, and `AndroidAutoView` shows its placeholder by it.
- **The phone takes its frame, shape and size, once, when it connects.** A start with the window closed (autostart, or the car's own button) has no view to measure, so the window remembers the exact physical size its view reports (same constraints, same `MediaQuery` pixel ratio as `AndroidAutoView`) and the service hands it to `controller.setViewSize` before `start()`. Any difference from what the view later reports makes the phone lay out again, which drops the picture for a moment.
- **A phone takes the density (`dpi`) and the sensors once, when it connects.** `setDpi`/`setSensors` change them for the next connection, so the driver's size and "use the car's GPS" never need a restart, only a reconnect; the service notes what the connected phone got to say so in Settings. The dpi is worked out from SmartifyOS's canvas pixel ratio (`androidAutoDpi`, from what the window's `MediaQuery` said last time), so Android Auto's size follows SmartifyOS's and the screen's resolution only decides how sharp it is.
- **Stopping bounces the phone's USB and Bluetooth**, which looks exactly like a phone arriving. That is what the autostart cooldown in `AndroidAutoService` is for.
- **Whether a phone is on the cable comes from `controller.phoneOnUsb`** (and `phoneOnUsbChanges` for starting on its own), on every platform, never from reading USB devices here. A session that will not offer Wi-Fi is `start(transports: {usb})`, so no hotspot comes up just to be declined; `startWireless()` still works on it later.
- **On Android SmartifyOS cannot see who is on Bluetooth** (core has no Bluetooth backend there). So a session there offers Wi-Fi to any paired phone (an empty `AndroidAutoWirelessConfig`, which makes the plugin host Android's own hotspot and prod the paired phones), and "start on its own" with wireless on also starts with the car. The permissions are asked for when a session starts (`AndroidAutoPermissions`). With one phone, test through Android Auto's head unit server (Developer options, Android Auto).
- Anything wrong or missing in the plugin gets an issue on FlutterAndroidAuto (`gh issue create`) and is fixed and released there, rather than worked around here.
